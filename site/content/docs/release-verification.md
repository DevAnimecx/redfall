**A RedFall release is verifiable in three steps: check the SHA-256 hash, verify the Sigstore attestation, and run the installed wheel from outside the checkout.** The checks establish that the file you downloaded is the file that was published and that it came from the repository's release workflow. They do not establish that software is "virus free"; no honest provenance check can promise that.

This page explains each check, the commands, and the limits.

## What is published with a release?

The v0.1.1 release publishes:

- `redfall-0.2.0-py3-none-any.whl` — the pure-Python wheel.
- `redfall-0.2.0.tar.gz` — the source distribution.
- `SHA256SUMS` — the hashes for both artifacts.
- A Sigstore build attestation generated by the release workflow.

The wheel has no compiled extensions, no post-install hooks and no vendored code. The runtime dependencies are declared in `pyproject.toml`.

The published v0.1.1 assets were downloaded and verified on 2026-10-21:

## How do you check the hash?

Download the artifacts and `SHA256SUMS` into the same directory, then run:

```bash
sha256sum -c SHA256SUMS
```

On Windows PowerShell, compute the hash and compare it to the published line:

```powershell
Get-FileHash .\redfall-0.2.0-py3-none-any.whl -Algorithm SHA256
```

If the hash does not match, stop. Do not install the file.

## How do you verify the Sigstore attestation?

With the GitHub CLI:

```bash
gh attestation verify redfall-0.2.0-py3-none-any.whl --repo DevAnimecx/redfall
```

The attestation is bound to the release workflow and the tagged commit. The command verifies the signature and the provenance statement. A successful check means the artifact was produced by that workflow from that repository, not that the code has been audited for every possible bug.

If you do not have `gh`, install it from GitHub's releases, authenticate, and run the same command. The attestation is public.

## How do you prove the installed wheel behaves?

`scripts/verify_wheel.py` installs the wheel into a fresh virtualenv, runs it from a directory outside the checkout, and requires it to parse, taint and find the interprocedural flow. The point is to catch a wheel that only works because it can see repository files.

The wheel carries the runtime files it needs: the sandbox harness (`redfall.validation`), the agent prompts and the sandbox Dockerfile. The verification is part of the release process, not a claim about a different artifact.

## How do you rebuild from source?

If you do not want to trust a download at all, build from the tagged source:

```bash
git clone https://github.com/DevAnimecx/redfall.git
cd redfall
git checkout v0.1.1
python -m build
```

The build produces the same wheel layout. `scripts/verify_wheel.py` then proves the installed wheel behaves. Rebuilding does not require the release attestation; it replaces trust in the artifact with trust in the source and your build environment.

## What does the attestation prove?

| Check | What it establishes | What it does not establish |
| --- | --- | --- |
| SHA-256 | The file is byte-identical to the published file | That the published file is safe |
| Sigstore attestation | The artifact came from the release workflow and tagged commit | That the code is free of vulnerabilities |
| Wheel verification | The installed package can parse and taint outside the checkout | That every runtime path works |
| Rebuild from source | The source produces a wheel with the same layout | That your environment matches the release environment |

The distinction matters because "verified" is often used to mean "trustworthy in every respect." Here it means provenance and behaviour checks with named limits.

## What is not claimed?

RedFall does not claim that a release is "virus free," "unhackable," or safe to run against systems you do not own. It executes target code by design. The [security page](/docs/security/) explains the threat model and the range-target warning.

It also does not claim that the attestation covers the target applications in `range/`. Those are deliberately vulnerable test applications, not release artifacts.

## How do you report a supply-chain concern?

Use GitHub's private vulnerability reporting on the repository: **Security** → **Report a vulnerability**. Do not open a public issue for an exploitable supply-chain problem. Include the version, the artifact hash and the smallest reproduction you have.

## Frequently asked questions

### Do I need to verify every release?

If you install a published artifact, yes. The checks are fast and they are the difference between a verified download and a trusted one.

### Is the wheel signed with a long-lived key?

The release uses Sigstore build attestations tied to the GitHub Actions workflow identity. Verify with `gh attestation verify`; the command checks the identity and the provenance.

### Can I install from the repository instead?

Yes. `pipx install git+https://github.com/DevAnimecx/redfall` installs from source. That path has different trust properties: you are trusting the repository and your package installer rather than a release artifact.
